# ADR-0015: Python 3.14 as the single workspace Python

Status: Accepted
Date: 2026-10-22

## Context and Problem Statement

A uv workspace enforces one `requires-python` across its members, so infrastructure, services and SDK share one Python
floor while they live in one workspace ([ADR-0012](0012-uv-workspace-monorepo.md)). The services run
on AWS Lambda, so the Python they target must be a Lambda runtime that the CDK library can name. The
SDK runs on researchers' own machines, where older Pythons are common. The question is which Python
the workspace targets now.

The SDK runs on Python 3.14 now, and a wider floor is left for a later decision.

## Considered Options

- Python 3.14 for every member.
- Python 3.15.
- An older floor (3.10 to 3.12) for every member, so the SDK reaches more researchers.
- Split floors: 3.14 for infrastructure and services, older for the SDK.

## Decision Outcome

Chosen option: "Python 3.14 for every member", because 3.14 is the newest Python that both a
generally available Lambda runtime and the current CDK library support.

The aws-cdk-lib v2.274.0 Lambda runtime list stops at `PYTHON_3_14`: it defines `PYTHON_3_10` through
`PYTHON_3_14` and no `PYTHON_3_15`. Lambda's `python3.15` runtime is a public preview only. The workspace pins `.python-version` to `3.14`,
and every member declares `requires-python = ">=3.14"`. ruff targets `py314`.

### Consequences

- Good: one Python everywhere; local development, tests and Lambda run the same version.
- Good: the newest language features and typing behaviour from the first line of code.
- Bad: researchers on older Pythons, common in conda-based neuroscience setups, cannot install the
  SDK. This is the main cost, and it
  falls on the SDK, the platform's primary product surface.
- Bad: the decision ages when Python 3.15 reaches Lambda; GA is targeted for November 2026.
- Watch item: when Lambda `python3.15` is generally available and aws-cdk-lib defines
  `PYTHON_3_15`, this ADR gets a dated update that bumps the version.
- Review point: the SDK's Python floor is decided later. If the SDK needs an older floor than the
  services, that decision also covers how the workspace accommodates it.

## Pros and Cons of the Options

### Python 3.14 everywhere (chosen)

- Good: newest Python with a generally available Lambda runtime and a CDK constant.
- Bad: excludes researchers on older Pythons until the SDK floor is decided.

### Python 3.15

- Bad: Lambda support is preview only, and aws-cdk-lib 2.274.0 has no constant for it (see above).

### An older floor for every member

- Good: the SDK installs on more researchers' machines.
- Bad: the services and infrastructure would be held to an older language for the SDK's sake, and
  the strict ruff target would drop with it.
- Deferred: the SDK floor is decided later, with the SDK's real dependencies in hand.

### Split floors

- Bad: a uv workspace enforces one `requires-python` across members, so split
  floors mean taking the SDK out of the workspace, which reopens the repository layout.
- Deferred together with the option above.

## Update (2026-10): Accepted

Researchers get Python 3.14 through uv in a private environment, so the SDK floor stays at 3.14 and outsiders need no system Python. A headless run of the install and first-hour steps on a clean machine passed on that basis (174 s). The Status is Accepted.

## Current state

Every workspace member targets Python 3.14. The reason is that 3.14 is the newest version that both a generally available Lambda runtime and the CDK library support. It holds: `.python-version` says 3.14 for every member. Check the Lambda runtime list again before moving to a newer Python. Nothing replaced it.
